# ClassRegister — Application Overview

_A description of what this application is and how it is put together, based on a read of the
codebase at commit `43ace1f` (branch `master`)._

> **Note:** this document describes the application as it was *before* the Ruby/Rails upgrade.
> The domain model, request surface and views in sections 1–4 are unchanged, but the stack in
> section 6 is now Ruby 4.0.6 / Rails 8.1.3.1, and several of the observations in section 7 have
> since been fixed. See [upgrade-notes.md](upgrade-notes.md) for what changed.

---

## 1. What it is

**ClassRegister** is a small Ruby on Rails web application for tracking magic classes: the
chapters (locations) where classes are run, the teachers who run them, the students who attend,
a register for each class session, and a per-student record of attendance and points.

The Rails application module is `ClassRegister` (`config/application.rb`). The repository lives
under a `mwb/` parent directory and the maintainer's email is on the
`magicianswithoutborders.com` domain, which strongly suggests this was built for **Magicians
Without Borders**, the charity that teaches magic to children in under-served communities. That
attribution is inferred from paths and authorship rather than stated anywhere in the code, so
treat it as context rather than fact.

Functionally it is a **CRUD scaffold application**. Every controller, view and JSON template was
generated by `rails generate scaffold` and left essentially untouched. Two features were then
hand-added on top of the scaffolding:

1. **File attachments on a classroom register** — one audio file and many images, via Active Storage with direct uploads.
2. **In-browser audio recording** — a record/stop widget that captures microphone audio and attaches it to a register.

There is no authentication, no authorization, no landing page, and no root route. Anyone who can
reach the server can read and modify everything.

## 2. Domain model

Five tables, all created in a single burst of migrations on 2019-08-03, plus the Active Storage
tables added on 2019-08-09.

```
Chapter ──< Student ──< StudentRecord
   │                         │
   │                         └── (also belongs_to :chapter directly)
   ├──< ClassroomRegister >── Teacher
   └──< StudentRecord
                │
ClassroomRegister
   ├── has_one_attached  :audio
   └── has_many_attached :images
```

| Model | Table | Columns | Associations |
|---|---|---|---|
| `Chapter` | `chapters` | `name`, `country`, `city`, `started_at` (date) | `has_many :students`, `has_many :student_records` |
| `Teacher` | `teachers` | `name` | — (none declared) |
| `Student` | `students` | `name`, `birth_date` (date), `points` (int), `chapter_id` | `belongs_to :chapter`, `has_many :student_records` |
| `ClassroomRegister` | `classroom_registers` | `happened_at` (date), `attendees` (int), `description` (text), `chapter_id`, `teacher_id` | `belongs_to :chapter`, `belongs_to :teacher`, `has_one_attached :audio`, `has_many_attached :images` |
| `StudentRecord` | `student_records` | `desc` (text), `points` (int), `attended` (bool), `student_id`, `chapter_id` | `belongs_to :student`, `belongs_to :chapter` |

**A chapter** is a location where classes are taught — it carries a name, a country, a city and
the date the chapter started.

**A classroom register** is the record of one class session: when it happened, how many students
attended, a free-text description, which chapter and which teacher, plus the audio recording and
photos captured during the session.

**A student record** is a per-student, per-session note: whether they attended, how many points
they earned, and a text comment. Note that it links to a `Student` and a `Chapter` but **not** to
a `ClassroomRegister` — so there is no structural link between an individual student's record and
the specific session it belongs to. `points` is also duplicated: it lives both on `Student` (a
running total, presumably) and on `StudentRecord` (a per-record award), with no code keeping the
two in sync.

No model declares any validations, callbacks, scopes, or business logic. The model files contain
association declarations and nothing else.

## 3. Request surface

`config/routes.rb` is five lines of `resources`, giving standard seven-action REST routing for
each model:

```ruby
resources :student_records
resources :classroom_registers
resources :students
resources :chapters
resources :teachers
```

There is **no `root` route**, so hitting `/` yields a routing error in production and the Rails
welcome page in development.

All five controllers are byte-for-byte standard scaffolds: a `before_action :set_*` for the member
actions, `respond_to` blocks serving both HTML and JSON, and a strong-parameters method. They
still carry the generator's original comments, including the pre-2019 "white list" wording.

The only controller that deviates from a pure scaffold is `ClassroomRegistersController`, whose
permitted parameters were extended to accept the attachments:

```ruby
params.require(:classroom_register)
      .permit(:happened_at, :attendees, :description, :chapter_id, :teacher_id,
              :audio, images: [])
```

Every resource also has jbuilder templates (`index/show/_partial.json.jbuilder`), so each one is
usable as a read/write JSON API as well as an HTML UI.

## 4. Views and front-end

Views are the generated scaffold ERB — an index table, a show page, new/edit wrappers around a
shared `_form` partial. Styling is the generated `scaffolds.scss` plus one empty per-controller
stylesheet for each resource.

The classroom-register form is the one hand-edited view. It adds:

- `form.file_field :audio, direct_upload: true` and `form.file_field :images, multiple: true, direct_upload: true`
- A `#controls` div with `#recordButton` and `#stopButton`
- A `#recordingsList` list where finished recordings are appended
- A `<script>` tag pulling **Recorder.js from `cdn.rawgit.com`**

The audio pipeline is `app/assets/javascripts/recording_audio.js`: it calls `getUserMedia`, feeds
the stream into a `Recorder` instance, and on stop produces a WAV blob that is added to the list
and uploaded. `app/assets/javascripts/upload.js` renders Active Storage direct-upload progress
bars by listening for the `direct-upload:*` events, and `classroom_registers.scss` styles them.

The remaining `.coffee` files (`chapters`, `students`, `teachers`, `student_records`,
`classroom_registers`) are **empty generator stubs containing only comments** — no CoffeeScript is
actually written anywhere in this project. The same is true of four of the six `.scss` files.

Assets are served by **Sprockets** with a manifest-directive `application.js` requiring
`rails-ujs`, `activestorage`, `turbolinks` and then `require_tree .`. `package.json` exists but
declares **zero dependencies**, and there is no `node_modules`, no Webpacker and no bundler config
— the front end is entirely Sprockets plus one CDN script.

## 5. Storage and configuration

- **Active Storage** is used for the register attachments, with `config.active_storage.service = :local` in development (files land in `storage/`, which is git-ignored).
- **`mini_magick`** and **`image_processing`** are in the Gemfile so that `file.variant(resize_to_limit: [100,100])` works on the register's show page. This needs ImageMagick installed on the host.
- **Databases are split by environment**: `sqlite3` in the `development, test` group, `pg` in the `production` group.
- `config/credentials.yml.enc` is committed; `config/master.key` is git-ignored, so the credentials cannot be decrypted without that key being supplied out of band.

## 7. Observations worth knowing

These are things a reader of the code should be aware of. They are stated as findings, not as a
work plan. **Several have since been addressed** — the production database configuration and the
Active Storage schema gap were both fixed during the upgrade, and the dead gems were replaced.
See [upgrade-notes.md](upgrade-notes.md) section 7 for which of these remain open.

**The production database is not configured.** The `production:` key in `config/database.yml`
contains only comments — no `adapter`, no `database`, no `url`. As written, booting in production
would fail to connect. The `pg` gem is present and the recent commits (`added pg`, `added
dtabase yml`, `db try`) suggest this was mid-setup and never finished.

**The audio player on the register show page is inverted.** The template reads:

```erb
<% unless @classroom_register.audio.attached? %>
  <%= audio_tag(rails_blob_url(@classroom_register.audio), ...) %>
<% end %>
```

This renders the player only when **no** audio is attached — and calling `rails_blob_url` on an
unattached attachment will raise. The condition should be `if`, not `unless`.

**The Recorder.js CDN is dead.** `cdn.rawgit.com` was shut down in October 2019, two months after
this code was written. The `<script src="https://cdn.rawgit.com/mattdiamond/Recorderjs/...">` tag
in the register form no longer resolves, which means `recording_audio.js` will throw on
`new Recorder(...)` and the record button will not work. The library needs to be vendored or
sourced from a live CDN.

**`recording_audio.js` runs on every page.** It is picked up by `require_tree .`, and it calls
`recordButton.addEventListener(...)` unconditionally on `DOMContentLoaded`. On any page without a
`#recordButton` element — which is every page except the register new/edit forms — that is a
`TypeError` on `null`, and it will abort the rest of that script.

**Several gems are end-of-life.** `chromedriver-helper` was yanked from RubyGems in 2020 (Selenium
now manages drivers itself), `coffee-rails` and `turbolinks` are no longer part of modern Rails,
and `sass-rails` 5.x depends on the deprecated Ruby Sass implementation.

**The Active Storage schema predates several Rails changes.** The committed migration is the Rails
5.2-era version. Rails 6.0 added a `service_name` column to `active_storage_blobs`, 6.1 added the
`active_storage_variant_records` table, and 7.0 relaxed the `NOT NULL` on `checksum`. Any upgrade
past 5.2 needs those follow-up migrations applied.

**There is no authentication or authorization of any kind.** Every route is world-readable and
world-writable, including the JSON endpoints. Given that the data consists of the names and birth
dates of children, this is worth weighing before anything is exposed publicly.

**`StudentRecord` has no link to a session.** As noted above, records attach to a student and a
chapter but not to a `ClassroomRegister`, so "which class was this record taken in?" is not
answerable from the schema.
